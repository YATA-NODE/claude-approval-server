# 採否表(案C Phase 0 → Phase 0.5 go/no-go の判定材料)

master plan が go/no-go の必須材料として要求する表。**この表だけで判定できる**ことを目標に、
各行に corpus 参照(録画名 + sha256 先頭 16 桁)と再現回数を持たせる。

- 状態語彙: `verified`(コマンド / 再生で直接確認)/ `partial`(一部条件のみ)/ `unknown`(未測定)。
  **`verified` は「その事象が起きることを観測した」= 存在の証明**であって、再現率や全称的な保証ではない。
  再現性まで確かめた行にはその旨を明記する(存在反例と、安定して誘発できる攻撃は別物として扱う)。
- 観測回数の規約(`docs/attr-count-table.md`): **固定された録画を 1 回再生** / 実機での取得は 2 回。
  **これは「決定論だから 1 回でよい」ではなく「同じ入力・同じコード・同じ端末条件なら同じ結果になる
  という前提で 1 回に留める」という運用上の取り決め**。前提(再生コード・依存版・幅の固定)は
  別途担保が要るので、**1 回の再生は再現性の測定ではない**。本表の `verified` は
  「その条件で観測できた」であって「常にそうなる」ではない。
- 判定は **production の関数をそのまま呼んで**再現している(`parseDialog` / `readTabBarRow` /
  `__test.barRowIsCliDrawn` / `frameOf`)。述語の手写しはしていない。
- 対象環境 = `docs/attr-manifest.json` の `env-2026-08-10`(Claude Code 2.1.226 系 / node v20 /
  @xterm/headless 6.0.0 / TERM=xterm-256color)。**単一環境・単一 CLI 版の観測**であり、
  他の版・他の端末・他の tool 経路へ一般化しない。
- §1 の pilot 由来の行は、**現物のファイルを再生し直して再観測した**(観測時のファイルと同一である
  証明が無かったため。再生で同じ属性が出ることを確認し、その sha256 を manifest に固定した)。

### 判定規則の正本(この表を単独で読めるようにするための引用)

master plan(`~/.claude/plans/sonnet-codex-tender-sedgewick.md`)から、判定に使う 2 つの規則を引く。
**規則の正本は plan 側**なので、plan を改訂したらこの引用も更新する。

- **Phase 0.5 の go 条件**: 「**R2(戻す一手の無条件許可廃止)が成立すること**」= 必須。加えて
  「**R1 の go 条件 = WebFetch / MCP の少なくとも一方で『同定して転送』が成立**」。
  転送成立が両方とも不能で fail-close 明示化のみに縮む場合は、**目的変更(縮小リリース)として
  ユーザー承認を必須**にする(勝手に v1.20.0 を出さない)。
- **独立オラクルの唯一の定義**: 「**PTY 描画を経ずに実 tool 名・引数を観測できる証跡のみ**」。
  次はいずれも独立オラクルに **しない** — ①承認枠と同じ描画表現から抽出した値
  ②ハーネスが投入したプロンプト。

### 1.1 「x=0 アンカー」が崩れた経緯(最重要)

Phase 0 の途中まで、**唯一残った差は列位置**だった。モデル出力は常に 2 列インデントされ(x≥2)、
tool 結果は `⎿` の後(x≥5)から描かれ、7 通りの攻撃すべてで x=0 に到達できなかった。

しかし `frameOf` は「最後の選択肢行から**上へ**最初の罫線行」を探す述語なので、攻撃者は
**偽の選択肢行だけを書き、罫線は画面に残っている本物を使う**ことができる。実測(frame #65)では
採用された罫線は **x=0..119 / fg=#888888 = CLI が描いた実物**で、選択肢行はモデルが書いた
装飾なしの平文だった。**列位置の条件は攻撃者が「満たす」のではなく「既に満たされているものを
指させる」**。

> **再現性(2026-08-14 に測定して更新)**: 当初は「142 フレーム中 1 フレームの存在反例」だったが、
> **同一手順で 3 回取得して 3 回とも発火・成立した**(`e2e-raw-b-borrow.log` frame #65 /
> `e2e-raw-b-repro1.log` frame #64 / `e2e-raw-b-repro2.log` frame #64・#65)。
> 3 本とも採用された罫線は **x=0..119 / fg=`rgb:8947848`(#888888)= CLI 由来**で、
> 選択肢行はモデルが書いた装飾なしの平文。**偶然の 1 フレームではなく、この手順では再現する**。
> 成立するのは再描画の過渡状態(入力欄の上端罫線が旧位置に残ったまま新しい応答テキストが
> 下へ流れる瞬間)で、**幅・スクロール・タイミングを変えたときの成立率は依然 `unknown`**
> (3 本とも同一幾何・同一手順)。
>
> **さらに区別すべきこと**: ここで示したのは **`frameOf` という述語の健全性への反例**であって、
> **end-to-end の誤転送(実際にスマホへ偽の承認が飛ぶ / キーが送られる)ではない**。
> 転送に至るには `parseDialog` の他の条件(終端マーカー等)も通る必要があり、
> **そこまで到達するかは測っていない(`unknown`)**。
> ただし wrapper は毎フレーム判定するため、**「安定して誘発できない」ことを防御の根拠にはできない**
> = 述語を作り直す理由としては十分。

### 1.2 `barRowIsCliDrawn` の前提が壊れている

この述語は「背景色セルがある = CLI が描いた行 = 信用できる」という含意で使われている。
実測では、**CLI は "自分が描いた行" と "内容が CLI 由来の行" を区別しない**:

- Bash 結果として直接描画された生 SGR の行 → 背景色が付く → `barRowIsCliDrawn()` = true。
  **frame #29-36 の 8 フレーム連続**(全 36 フレーム中)で、選ばれた行は y=12 `⎿  ☐ Q1  ☐ Q2  ✔ Submit`。
  **再現性 = 3 回取得して 3 回とも 100%**(元 8/8 / repro1 12/12 / repro2 8/8 = 候補フレーム
  28/28 すべてで true)。`readTabBarRow` は毎回同じ tool 結果行を選んだ。
- 生 SGR 無しでも、CLI がプロンプトのエコー行に背景色を付けて描く → 同じく true。
  **全 34 フレーム中 13 フレームで `readTabBarRow` が成立し、うち 10 フレームで true**
  (選ばれた行は y=9 のプロンプトのエコー行、fg=#FFFFFF / bg=`rgb:3618615`)。

前者は攻撃者(モデル)が内容を制御できる直接の攻撃面。後者は本ツールの脅威モデルでは
利用者自身の入力なので直接の攻撃面ではないが、**述語の前提が壊れていることの証拠**になる。

## 3. R1 / R2 / R3 の go/no-go 判定

master plan の Phase 0.5 条件に照らした判定。

### R1(ラベル無し枠の同定・転送)— **現時点で不成立(not demonstrated)**。恒久的な no-go とは言えない

go 条件は「**WebFetch / MCP の少なくとも一方**で『同定して転送』が成立すること」。

- **単独で採用できる属性シグナルが 0**(§1)。構造も属性も列位置も、単独では偽装・借用される。
  ただし **AND 合成条件は未定義・未評価**なので、「属性チャネルでは原理的に不可能」とまでは言えない。
- 加えて、**master plan が定義する独立オラクルを、現時点の調査範囲では確認できていない**。
  本ツールは PTY ラッパなので、claude の tool 名・引数は「CLI が描画した画面」としてしか
  観測していない。**ただしこれは「PTY 以外の経路を調べ尽くした」という意味ではない**。

#### 非 PTY 経路の調査結果(2026-08-14 実測)

必須条件 8 点(下記)に照らした評価。**無条件で採用できる候補は無いが、2 つの候補は性質が違う**。

| 条件 | transcript JSONL | PreToolUse hook |
|---|---|---|
| 1 相関 | **満たす(条件付き)** — `claude --session-id <uuid>` で起動すると transcript のファイル名と `sessionId` が一致。**現行 wrapper は `--session-id` を渡していない** | **満たす** — stdin JSON に `session_id` / `tool_name` / `tool_input` が乗る |
| 2 順序(承認確定より前) | **満たす** — `tool_use` の timestamp がダイアログ検出より 115ms / 137ms 早い(2 回実測) | **満たす** — hook 完了がダイアログ検出より 26ms / 41ms 先行(2 環境で実測) |
| 3 単回消費 | 未実装(`toolu_...` の一意 id があるので設計は可能) | 未実装(hook はイベントごとの一過性プロセスなので単回性は自然)|
| 4 完全一致 | 未設計(`tool_input` は構造化 JSON。画面文字列との突合せ正規化仕様が無い)| 同左 |
| 5 タイムアウト fail-close | 未実装 | 未実装 |
| 6 秘密情報 | **満たさない** — 生の引数が**無加工の平文で永続保存**される(実測) | 未確認(一過性なので「正規化ハッシュだけ書き出す」等の縮小開示を設計できる)|
| 7 信頼境界・改竄検知 | **満たさない(実測で確定)** — 同一ユーザー権限で `echo '{偽の tool_use}' >> file` が**何の制約もなく成功**した。ACL / immutable / 署名のいずれも無い | **入力チャネルは満たす** — stdin は CLI 本体が直接渡すのでモデル出力や tool 結果を経由できない。**出力チャネル(hook → wrapper の受け渡し)は未設計**で、そこは transcript と同じ改竄リスクを持つ |
| 8 symlink / TOCTOU | 構造的に無防備(`~/.claude/projects/<slug>/` は 0755 の通常ディレクトリ)| 出力チャネル次第(未設計)|

**判定**: **transcript JSONL は条件 7 で構造的に失格**(同一ユーザー権限の tool・子プロセス・MCP
サーバが偽エントリを書けるので、オラクル自体が誤承認の入口になる)。
**PreToolUse hook は入力チャネルが一段強い**(CLI 本体からモデル出力を経由せず直接渡る)。
残る課題は条件 6 / 7 / 8 に集中しており、**すべて「hook が結果をどこへ・どう書き出すか」という
未設計の出力チャネル**に帰着する。この環境には nonce ベースの challenge object の前例があり
転用の余地はあるが、**設計・実装しない限り自動的には満たされない**。

> **corpus の代表性に関わる注意(2026-08-14 に判明)**: Claude Code のセッション内から wrapper を
> 起動すると `CLAUDE_CODE_CHILD_SESSION` が継承され、**子セッションの transcript 保存が切れる**
> (`⚠ Transcript saving is off` が画面に出る)。素の端末から起動した場合は正常に保存される。
> **本 Phase 0 の録画・調査はすべて「継承」条件下で取得した**ため、実運用の画面とは
> 警告行 1 本ぶんレイアウトが異なる。描画属性そのものへの影響は測っていない(`unknown`)。

| その他の経路 | 状態 |
|---|---|
| MCP サーバ側のログ | 未調査 |
| CLI の構造化出力 / debug 出力 | 未調査(調査には `--debug-file` を使った = 存在は確認)|
| codex 側(tab notes) | 未調査 |

**master plan は「CLI 側識別子 / IPC / 承認トークンはサードパーティ CLI 本体の改修が必要」として
除外していたが、上記 2 つは CLI の改修を伴わない**(設定と既存の記録の利用)。この前提が
崩れている可能性があるため、**「構造的に取得不能」という以前の記述は取り下げる**。

**根拠の出所(仕様の断定を避けるため明示)**: transcript JSONL に `tool_use`(name + input)が
出ることは、**この環境の別用途の hook が実際にその形で読んでいる**という間接的な根拠に基づく
(`~/projects/dotfiles/.claude/scripts/check-response-time-review.sh` が
`.message.content[] | select(.type=="tool_use")` を jq で抽出している)。PreToolUse hook が
tool 名と入力を受け取ることも、同ディレクトリの書き込み検査 hook の存在が根拠。
**いずれも「対象 CLI 版でこの用途に使えるか」は未確認の仮説**であり、公式仕様の確認か最小実測が要る。

#### 非 PTY オラクルを「採用してよい」とするための必須条件(先に決めておく)

**単に「PTY を経ずに tool 名・引数が読める」だけでは不十分**。別セッションの記録・古いイベント・
実行後にしか出ない記録を取り違えると、**オラクル自体が誤承認の入口になる**。採用するなら
次を満たすことを条件にする(満たせない経路は不採用):

1. **相関**: その記録が「いま転送しようとしている承認要求」と一意に結び付く(session id +
   request id 等)。突き合わせ不能なら不採用。
2. **順序**: 承認が確定する**前**に書かれること。実行後にしか出ない記録は事後確認にしか使えない。
3. **単回消費**: 1 つの記録を 1 つの承認にしか使わない(古い記録の再利用を構造的に防ぐ)。
4. **完全一致**: tool 名と引数を正規化したうえで**完全一致**を要求する(部分一致・前方一致は不可)。
5. **タイムアウトは fail-close**: 記録が時間内に現れない / 読めない / 解析できないときは
   転送しない(「読めなかったから画面を信じる」という緩和分岐を作らない)。
6. **秘密情報**: 記録には引数がそのまま入る。**収集項目の最小化 / redaction / 保存先と権限 /
   削除期限 / fixture へ入れてはいけない情報**を先に規定する(権限と保持期間だけでは足りない)。
7. **信頼境界と改竄検知**: 「PTY を経ない」だけでは不十分。**同一ユーザー権限で動く tool・
   子プロセス・MCP サーバは、その記録に書き込める**(= 偽イベントを承認に結び付けられる)。
   誰が書けるファイルなのか、書き込み権限をどう絞るか、改竄をどう検知するかを決める。
   決められないなら、その経路はオラクルとして**不採用**。
8. **symlink / TOCTOU**: 読む前に実体を確認し(symlink 拒否・owner 検査)、
   読んだ内容と承認に使う内容が同一であることを担保する。

> **この条件表自体が「非 PTY オラクルは簡単ではない」ことを示している**。
> 調査で経路が見つかっても、7・8 を満たせなければ採用できない。
> **「読めた = 使える」ではない**。

- **codex 側(tab notes)も未測定(`unknown`)**。構造化要求が別経路に出るなら独立オラクルを
  取得できる可能性があるが、Phase 0 では測っていない。**測っていないものを「成立する」と書かない**。
- 現状の結論: **claude 側 T2 / T3 は「今の材料では転送を成立させられない」**。
  恒久的な不成立ではなく、上表が埋まるまでは判定を保留するのが正確。

### R2(戻す一手の無条件許可の廃止 / Profile B)— **not demonstrated(未実装・未証明)**

**まず状態を正確に**: Phase 0 は production を変更していないので、**R2 は実装されておらず、
合格基準(不変条件をテストで固定)も満たしていない = `not demonstrated`**。
以下は「実装すればどうなるか」の見込みであって、成立の主張ではない。
(T5 で `verified` なのは「確認画面でタブバー行が消えるフレームが実在し、そこで属性検証が
通らない」という**観測事実**までであって、Profile B の実装が合格することではない。)

- 「属性を確認できないフレームでは Shift+Tab を送らない」という不変条件そのものは実装できる。
  現行の無条件許可(`forwardTabDebt > 0` で属性ゲートより先に許可)を消す方向なので、
  **安全側と見込む**。ただし **「HEAD 以下」であることは未証明**: 分岐を 1 本消しても、
  状態の残留や後続入力による別経路の送出まで含めた送出集合が HEAD の部分集合になるとは
  自明でない。**到達可能状態 × 送出の差分テスト**で確かめるまでは「見込み」に留める。
- ただし **「属性を確認できた」の意味が薄い**(§1.2 でゲートの根拠が壊れている)。
  R2 の価値は「属性で真正性を保証する」ではなく「**無条件許可という経路を 1 本消す**」に縮む。
- 確認画面での可用性代償(戻れず Submit に残る)は実測済みで、PC 操作誘導の表示とセットで
  なければ既知の回帰を復活させる。

### R3(タブバー背景色依存の頑健化)— **no-go(現在の方向では)**

- 「背景色セル > 0」は採用不能(§1.2)。代替となる単独シグナルは見つかっていない。
- inverse は実機の CLI が使わないうえ攻撃側は作れるので、置き換え候補にならない。

### 総合(Phase 0.5 の go 条件との照合)

master plan の go 条件は「**R2 が成立すること(必須)** ∧ **R1 が WebFetch / MCP の
少なくとも一方で転送成立**」。

**R1 も R2 も現時点で満たしていない**:

| 要件 | 状態 | 未達の理由 | 埋めるのに要ること |
|---|---|---|---|
| R1(ラベル無し枠の同定・転送)| **not demonstrated** | ①評価した単独シグナルはすべて不採用 ②AND 合成条件が未定義・未評価 ③独立オラクルの非 PTY 経路が未調査 | 合成条件の定義 + holdout 評価 / 非 PTY オラクルの調査 |
| R2(戻す一手の無条件許可の廃止)| **not demonstrated** | Phase 0 は production 非変更なので**未実装**。合格基準(不変条件のテスト固定)も未達。「HEAD 以下」も未証明 | 実装 + 到達可能状態 × 送出の差分テスト + 実機 E2E ④ |
| R3(タブバー背景色依存の頑健化)| **no-go(現方向)** | 根拠にしていた「背景色セル > 0」が採用不能(§1.2)。代替の単独シグナルが無い | 述語の作り直し(Phase 1)|

言えるのは「**現時点で go 条件が未達**」であって「**恒久的に達成不能**」ではない。
R1 の未達要因 ②③ と R2 の未実装は、いずれも**追加の実測 / 実装で埋まりうる**。
master plan の規定どおり、**勝手に縮小リリースせず、中止 / 再設計 / 追加実測のいずれにするかを
ユーザーへ諮る**。

## 4. 件数表(fixture 112 件)の改訂案 — ユーザー承認事項

`docs/attr-count-table.md` は総計 112 件(真正 20 / 敵対 75 / 境界 5 / 枠内注入 12)を要求し、
「動かす必要が出たら中止条件の判定に入り、ユーザー承認へ送る」と自ら規定している。
**現状は 7 件**(真正 6 / 敵対 1)。この乖離をどう扱うかの提案:

### 提案: 凍結は「中止を選んだ場合のみ」。続行するなら拡充が要る(条件付き)

**中止する場合**: 112 件は「**採用シグナルが未定**」の段階で引いた計画値であり、敵対 75 件の目的は
「採用したシグナルについて偽陽性 0 を示す」ことにある。採用シグナルが 0 件で先へ進まないなら、
**偽陽性 0 を証明すべき対象が存在しない** = 追加生成の情報価値はほぼゼロ。凍結してよい。

**続行する場合(重要)**: 合成条件・枠内注入・過渡状態はいずれも未評価なので、**追加 corpus の
情報価値はゼロではない**。しかも「合成条件を確定してから敵対例を作る」順序は、**条件への過適合と
確認バイアス**を招く(自分の条件を通す例ばかり作る)。したがって続行を選ぶ場合は:

1. **条件を確定する前に**、状態軸(再描画 / 折返し / 幅 / 属性欠落)・生成規則・seed・判定閾値を
   **holdout として事前登録**する(登録は条件確定の**前**、生成と評価は確定の**後**、
   評価は**一度だけ**。作った後で採否条件を調整できないようにする)。
2. 少なくとも #8(借用)と #9(背景色ゲート)の**再現性**を測る(1 フレームの存在反例のままにしない)。
3. その holdout に対して合成条件が偽陽性 0 を保てるかで採否を決める。

**この節の提案は、私(メイン)の結論を守る方向に働きうる**という点を明示しておく:
「拡充しない」は「自分の no-go 判断を反証しにくくする」提案でもある。だから
**続行を選ぶ場合の拡充要件を上のとおり明文化**し、凍結は中止時に限定した。

- **実際に効いた敵対サンプルは少数の狙い撃ち**だった: 偽枠の生成(`e2e-raw-adv-fakeframe.log`)/
  罫線の借用(`e2e-raw-b-borrow.log`)/ 背景色ゲートの突破(`e2e-raw-a2-…` `e2e-raw-a-…`)の
  **4 本が結論を決めた**。系統的な網羅ではなく「残った差を 1 つずつ潰す」形で収束した。
- **真正側(偽陰性 0)の要求は緩めない**。ただし真正 20 件も「採用シグナルの検出漏れを測る」ための
  数なので、採用シグナルが確定するまでは同じく前倒しの意味が薄い。現状の 6 件
  (T1 / T2 cols=120 / T2 cols=80 / T3 / T4 / T5)は各種別 1 件ずつを満たしており、
  **回帰 corpus としては機能する**。

### この提案で落ちる保証(黙って減らさないための明示)

1. **状態軸(再描画 / 折返し / 幅 / 属性欠落)ごとの網羅**は失われる。現状の真正 6 件は
   種別ごと 1 件で、状態軸は cols=80 の 1 本以外は取れていない。→ Phase 1 で採用シグナルが
   決まった時点で、**そのシグナルに関係する状態軸だけ**を測り直す前提にする。
2. **⑥ 枠内注入(12 件)は未着手のまま**。これは「枠の真正性を同定できても、枠内テキストから
   args を復元する経路が別問題」という R8 系の要求で、**R1 が no-go でも T1(ラベル有り枠)には
   残る論点**。案C を続けるなら別途必要。
3. **境界ケース(部分再描画 5 件)も未着手**。ただし #8 の成立が**まさに再描画の過渡状態**で
   起きたため、「過渡状態を測る価値がある」ことは実測で裏付けられた。

### 代替案(ユーザーが拡充を選ぶ場合)

件数表どおり 112 件まで作るなら、**先に Phase 1 で採用シグナル(AND 合成条件)を確定**してから
着手すべき。順序を逆にすると、確定前の条件に対して 105 件を作り、確定後に作り直すことになる。

## 5. 推奨(メインの意見。決めるのはユーザー)

**推奨 = 「案C を当初の形のまま v1.20.0 として出すことはしない。ただし Phase 0 で判明した
3 点は独立に価値があるので切り出し、R1 の判定は追加実測で確定させる」**。

理由は §3 のとおり、**単独で採用できる属性シグナルが 1 つも無い**こと、そして

「無い」ではなく「調べていない」であり、ここが埋まると判定が変わりうる。

これは失敗ではなく **Phase 0 が意図どおり機能した結果**である。実装前に「今の設計では
成立しない」を確定できた(master plan が Phase 0 を「production 変更なしの実測」と定めた狙いに合致)。
